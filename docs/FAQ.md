# 技术常见问题 FAQ

> 每条都对应仓库里的真实产物，数字可复现。

## Q1 没有硬件，你怎么证明它能平衡？

**答**：分两层，外加一层诚实声明。

1. **算法层（主机单测）**：控制算法与硬件完全解耦（Service 层零 HAL 依赖），
   同一份 C 源码在 PC 上用 gcc 编译，CTest 跑 111 条断言——三环方向性/三级限幅/
   卡尔曼收敛与零偏估计/协议 10 万字节模糊测试，`Service/` 行覆盖 98.5%。
2. **闭环层（固件在环 SIL）**：写了 1D 倒立摆-小车动力学模型（含电机一阶惯性、
   编码器量化、MPU 噪声与零偏随机游走），**跑的是要烧进芯片的同一份 App+Service
   源码**，只换 Port 实现。E1 初始倾角 10° 恢复 1.16s 进 ±0.5°；E2 冲击恢复
   1.22s；E3 台架卡尔曼 RMS 0.091° 显著优于互补 1.88°、纯积分 30°；E4/E5 给出
   参数与周期抖动的量化趋势；E6/E7 验证倾角锁存保护与欠压降功率。
   七组实验中 E1/E2/E6/E7 作为硬验收进了 CTest（7/7）。
3. **边界**：模型参数是按公开规格估算并做过标定的（约束 = 默认增益可稳），
   摩擦、机械安装角、真实噪声谱与实车有差异，所以结论只讲**趋势与相对比较**，
   不声称绝对精度。若后续拿到板子，第一优先是补驱动级实测。

## Q2 卡尔曼的 Q_angle / Q_gyro / R_angle 怎么定的？

**答**：三步。
1. **按物理意义给初值**：R 由加速度角度噪声方差估（0.5，对应振动环境下角度噪声
   ~0.4°量级）；Q_angle 是模型预测本身的过程噪声（0.001）；Q_gyro 决定零偏估计
   的收敛速度（0.003，太小则漂移修不掉，太大则零估计"抖"）。
2. **实验扫参**：E3 台架实验（固定 10°、注入 1.5°/s 零偏 + 随机游走）对比不同
   Q/R 下的稳态 RMS 与零偏收敛时间，取折中。
3. **强调 dt**：dt 必须等于真实采样周期（本工程 `Car_Config.h` 里 `dt` 与
   `vTaskDelayUntil` 周期同源宏绑定）。dt 错一倍 → 预测步 `angle += ω·dt` 增益
   错一倍，滤波过度信任陀螺，收敛变慢甚至发散——这是问题清单 #3 修过的坑。

**实测数据**：30s 台架、零偏 1.5°/s 条件下，卡尔曼 RMS 0.091°、互补(α=0.99)
1.877°、纯积分 30.0°（`docs/sil/e3_filters.png`）。

## Q3 控制周期抖动多大？怎么测？

**答**：
- **固件侧**：PID 任务是最高优先级(5)且由任务通知驱动，统计相邻两次唤醒的 tick
  差（min/max），每 10s 打印到 USART1（代码在 `App_Task.c`，`App_Task_GetPeriodStats()`
  可供调试器/CLI 读取）。设计上消除抖动来源：控制链路优先级 > OLED 显示(2)，
  显示刷屏不会打断闭环；采样用 `vTaskDelayUntil` 绝对延时防止周期漂移。
- **SIL 侧（E5）**：给物理步进注入 ±1/2/5/10ms 抖动而固件 dt 恒为 10ms（模拟
  "周期不确定"），量化结论：收敛时间 1.16→1.19→1.20→2.27→3.58s、稳态 RMS
  0.070→0.207，**单调劣化**——这就是坚持确定性周期的证据（`docs/sil/e5_jitter.png`）。
- 真实板子上的绝对数值需要硬件，如实说"机制和统计代码已就位，实测数据待上板"。

## Q4 FreeRTOS 栈溢出怎么定位？

**答**：
1. `configCHECK_FOR_STACK_OVERFLOW = 2`（双校验：末尾 pattern + 溢出检测）+
   `vApplicationStackOverflowHook`：钩子里**只**把出错任务名抄进全局变量
   `g_stack_overflow_task`（调试器可直接读）、关中断停机——故障现场不用
   printf/串口，避免二次死锁（这是设计决策，不是偷懒）。
2. 事后：`uxTaskGetStackHighWaterMark` 水位已接入 `@ST#` 状态输出，随时可查。
3. 创建时按最坏路径估算（`sprintf`+浮点是大头），本工程 128 word × 4 任务，
   FreeRTOS 堆 15KB 统一管理。RAM 紧张（静态占用 94%）是已知约束，所以
   栈水位监测是必需项而非锦上添花。

## Q5 任务通知和队列的区别，为什么这里用通知？

**答**：
- **通知**：轻量单槽、O(1)、无内存拷贝、无阻塞分配——适合"采样→控制"这种
  一对一、只要"发生了"不携带数据的唤醒。本工程数据通过共享变量传递（采样
  先写完，控制再读，顺序由通知保证）。
- **队列**：多生产者/需要缓冲/需要携带数据拷贝时用。
- 本工程三处同步：采样→PID（通知）、UART 字节→协议（中断上下文直接调用，
  状态机纯内存操作）、显示任务（纯周期，无需同步）。
- 量化对比（同场景 1000 次计时）列为后续实测项，没测之前不报数。

## Q6 HAL 和寄存器的区别？I2C 读一个字节的流程？

**答**：
- **HAL**：句柄 + 回调 + MspInit 的分层抽象，代码可移植、开发快，代价是间接层
  与运行开销；**寄存器**：直接写 `RCC->APB1ENR` 使能时钟、配 `I2C_CR1/CCR/TRISE`，
  时序完全可控，是理解外设的必经之路。
- **软件模拟 I2C 读一字节**：起始条件（SCL 高时 SDA 下降）→ 发地址字节 0x68<<1|0
  → 从机 ACK（SCL 低时读 SDA）→ 收 8 位（每 bit：SCL↑ 采样）→ 主机 NACK 最后一位
  → 停止条件（SCL 高时 SDA 上升）。每一步的建立/保持时间对应数据手册 tHD;STA/tSU;DAT。
- 本工程 HAL 版用硬件 I2C（`HAL_I2C_Mem_Read/Write`）；寄存器版双实现用
  `BSP_USE_REG` 编译开关切换（见 `BSP/`）。

## Q7 为什么直立环用 PD 不用 PID？

**答**：
- 积分会"追角度"：车身偏 1°，积分持续累积直到把车推过头，形成过冲-回摆，
  对快速倒下的小车是负作用；稳态偏差（机械安装角、重心偏移）由**速度环的积分**
  吸收更合适——它周期长、不催振。
- 微分项直接用陀螺角速度做阻尼，抑制 kp 引起的振荡。
- **E4 就是讲这个的**：kp 从 -400 扫到 -1040，-400 扶正不足直接发散；-560→-1040
  全部稳定但超调单调上升（1.96°→5.59°），说明阻尼不足时增大比例会换来振荡——
  有图有数据（`docs/sil/e4_metrics.png`）。

## Q8 项目里最难的一个 bug？

**答（挑 1~2 个，按"现象→假设→定位→修复→回归"讲）**：

1. **`dt` 与真实采样周期不匹配**（问题#3）：现象是滤波在动态工况下"跟不上"
   且有轻微发散趋势；假设是预测步增益错；定位手段是把 `dt` 和 `vTaskDelayUntil`
   的实参打印出来对比——一个 0.005、一个 0.01；修复是引入 `Car_Config.h` 单一
   源宏 `CAR_SAMPLE_PERIOD_S` 让两者编译期绑定；回归是 E3 台架实验 + 单测。
2. **临界区内自删除**（问题#7）：`vTaskDelete(NULL)` 写在 `taskEXIT_CRITICAL()`
   之前——自删除后还要执行临界区退出序列，等于踩自己的任务栈。修复是先退临界区
   再自删除。属于"实测能跑但依赖实现细节"的隐患，代码走查发现的。
3. **仿真标定翻车**（本轮真实故事）：首版倒立摆电机常数取 2.0 m/s²，临界角只有
   11.5°，E1 初始 10° 加上电机滞后直接穿帮翻车；用"默认增益必须收敛"做约束
   网格搜索，才把参数钉在 A_FULL=6.5 / TAU=8ms / C_V=4.0——**这个过程本身就是
   "参数辨识"的完整闭环**，标定依据全写在 `Host/sim/pendulum_model.h` 头注释里。
